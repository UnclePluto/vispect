# 患者扫码填写与医生修订设计

- 日期：2026-10-16
- 项目：智观云健康管理平台（简称「智观云」）
- 状态：整体方案与书面设计均已获用户确认（2026-10-16）；本会话逐项实施完成，独立评审的 3 项重要问题已修复，修复后的完整回归通过；尚未整合或部署。
- 基础：现有手机号后台登录、多机构切换、患者／研究／访视、动态表单、工作人员代录、答案修订及 PostgreSQL 强制 RLS。
- 与已有设计的关系：新增患者独立登录和自填能力；替代原有“患者表单全部由工作人员代录”规则，并放宽进行中研究内患者答案的修订范围。工作人员登录、机构隔离、研究流程、医生表单锁定规则继续生效。

## 1. 目标、已确认规则与范围

打通“医生创建患者并纳入研究 → 从表单生成填写链接和二维码 → 患者登录并填写 → 医生查看提交及带原因修订”的完整链路。患者页面适配手机和电脑，复用已发布表单版本及现有题型、条件显示和跳题规则。

用户已确认：

1. 新开通患者账号的默认密码统一为 `888888`，首次登录强制修改；完成改密后才能获取或填写患者表单。
2. 同一研究的同一访视表单共用链接和二维码。患者登录后仅能访问与自己明确绑定的患者档案所对应的任务。
3. 研究仍进行中时，医生可修订已经完成访视中的患者答案，每次必须填写原因并保留完整历史；修订不改变访视进度。
4. 整体采用独立患者入口，复用现有表单、答案和修订历史。
5. 创建患者时可同步开通填写账号，已有患者可补开通；同一手机号可以明确绑定多个患者档案，不能仅凭联系方式相同自动授权。
6. 提供草稿保存、继续填写和正式提交。患者提交后只读，由医生按现有流程确认完成访视。
7. 后台区分患者自填和工作人员代录。停止随访或研究结束后保持只读。

本轮包括账号开通、首次改密、登录退出、共用入口管理、患者草稿和提交、提交来源展示、医生修订及浏览器验收。不增加短信验证、自助注册、密码找回、微信身份、小程序、消息推送、新题型或自动完成访视。

## 2. 方案选择与模块边界

选择“独立患者认证与页面，复用研究及答案模型”。患者身份不加入现有工作人员的 `Account.role`，避免现有按机构授权的后台接口将患者当作机构成员。患者自填与工作人员代录写入同一份访视表单答案，后台、访视完成检查和导出使用同一数据来源。

其他方案的取舍：直接扩展工作人员角色需要全面调整既有成员、空间切换和后台权限；另建问卷及提交模型需要同步两套答案、访视状态与导出。两者的影响范围都超过当前需求。

新增 `patient_portal` 业务模块，分别承担患者认证、患者档案授权、表单入口、填写和患者操作记录；继续使用现有 `forms` 解释器和 `followups.Answer`／`AnswerRevision`。前端新增 `/patient/` 页面和独立请求封装，不挂载后台布局、工作人员认证状态及机构切换逻辑。

## 3. 患者账号与档案绑定

### 3.1 身份与手机号

患者登录身份按“机构＋规范化手机号”唯一。同一手机号在不同机构的患者账号分别管理，由扫码入口确定机构，不要求患者输入机构标识。手机号格式复用现有大陆手机号规范化规则。

患者认证独立于工作人员 `LoginIdentity`：同一手机号可同时作为医生和患者使用，开通患者账号、患者改密和患者退出均不修改工作人员密码或会话。

一个患者账号可以关联本机构多个患者档案，用于家庭共用号码；一个患者档案只关联一个患者账号。医生须在获授权患者档案上明确执行开通或绑定。患者联系方式用于联系，不能作为自动授权、自动合并或修改登录手机号的依据。

### 3.2 开通入口

新增患者弹窗提供“开通患者填写账号”选项及登录手机号；联系方式符合格式时可预填，仍须通过明确选项确认开通。未开通时保留原有可不填手机号的建档行为。

患者详情提供“开通填写账号”；已开通后展示登录手机号、是否可用和首次改密状态，不展示密码哈希。登录手机号不随普通联系方式编辑而变化。本轮不提供换绑、账号整体停用或密码重置；开通记录不能被普通患者编辑接口覆盖。

账号未存在时创建，保存 `888888` 的 Django 密码哈希并设置首次改密标记；已经存在时只增加明确的患者绑定，保留原密码和首次改密状态。重复开通返回已有绑定，不重复创建账号、绑定或审计记录；并发开通依靠机构手机号唯一约束和行锁处理。

创建患者并同步开通时，患者、负责医生关系、账号、绑定、配额与工作人员审计在同一业务数据库事务中提交。失败后不得留下半份账号或患者。补开通不额外占用患者配额。

### 3.3 密码与会话

`888888` 仅作为新账号初始密码的明确例外，不放宽正常改密规则；新密码沿用系统现有不少于 12 位、常见密码及纯数字校验，并且不能与原密码相同。

首次登录后只允许读取最少认证状态、修改密码和退出；患者列表、表单定义、草稿和提交接口都在服务端检查首次改密标记。登录错误统一为“手机号或密码不正确”，未验证凭据前不返回手机号是否开通、患者身份或入组情况。

使用独立的患者 HttpOnly 会话 Cookie（名称 `vispect_patient_session`，测试环境可配置），限定 `/api/patient/` 路径，`SameSite=Lax`，HTTPS 时启用 Secure。Cookie 只保存高熵随机会话凭据，数据库保存其摘要、患者身份、到期时间、密码版本和会话令牌。患者会话期限与现有工作人员会话配置一致。

登录轮换会话凭据；改密保留并轮换当前会话、撤销该账号的其他患者会话；退出撤销当前患者会话。每次患者请求重新检查机构、账号、密码版本与有效期。工作人员 Cookie 不认证患者接口，患者 Cookie 不认证后台接口。

患者 Cookie 不共享跨机构登录：扫描另一机构二维码时需要登录该机构的患者账号。成功切换患者登录机构后旧页请求必须因会话令牌不匹配而被拒绝，不能把旧患者输入写入新机构。

## 4. 共用填写链接和二维码

### 4.1 入口粒度与后台操作

一个入口严格关联一个 `FormBinding`，即固定“机构＋研究＋访视定义＋已发布表单版本”，且填写对象必须为患者。相同表单在不同研究或访视中使用时分别生成入口。

表单列表／表单详情增加“患者填写入口”，选择本人有权查看的引用研究及患者访视绑定；研究的“访视与表单”中也提供同一入口。已有有效入口直接展示；提供复制链接、二维码预览、下载二维码、停用及重新生成。使用 Ant Design 自带 QRCode，不额外引入二维码依赖。

只有机构管理员或该研究的医生成员可以管理入口。表单作者身份本身不授予其他研究的入口管理权；临床答案与患者列表仍要求既有患者负责关系和研究成员资格。

研究进行中、表单未暂停且未删除、绑定属于非筛选访视且有效，并且研究已有至少一名正式入组患者时允许首次生成或重新生成入口。其他状态允许获授权工作人员查看已有入口或停用。筛选期患者自填不在本轮范围内；筛选期继续由工作人员按现有流程代录。

每个绑定最多一条当前有效入口，不设置自动到期。停用后原链接失效；重新生成会原子撤销旧入口并创建新随机令牌，旧二维码随即失效。未保存的患者输入不能通过失效入口提交，已保存答案不被删除。

### 4.2 链接与解析

链接形式为 `/patient/fill/<token>`，令牌由至少 32 字节密码学随机数生成，不包含患者姓名、手机号、病历号或可推算业务 ID。二维码仅编码这条链接。

为支持后台再次展示、复制同一共用链接，入口记录保存随机令牌及唯一摘要；记录受机构 RLS 和工作人员权限保护，不写入审计变更正文。会话凭据与入口令牌分开管理，共用入口本身不承担患者身份认证。

未登录扫描有效入口仅展示患者登录页面；不返回患者清单、表单题目或答案。入口解析只返回完成认证路由所需的机构 ID 与入口 ID。入口不存在、停用或所属对象已删除时统一展示“填写链接已失效，请联系医生”。

### 4.3 登录后的任务匹配

服务端以已认证患者账号的明确绑定为起点，匹配入口所属研究中的正式入组记录及该访视实例。不得只凭请求中的患者 ID 或手机号查找任务。

一个账号仅有一名符合条件的患者时直接进入任务；多个时先选择患者，列表只展示本账号已绑定且加入该研究的患者。没有匹配项时提示“暂无对应填写任务，请联系医生”，不提供其他患者、研究或访视信息。

当前、尚未完成的正式入组访视允许新填或保存草稿。未来访视显示“尚未开放”；已提交显示提交成功及只读答案；已完成但未提交的非必需表单显示“该访视已完成，不能补填”。暂停研究／表单、已停止随访、已完成全部随访或已结束研究，展示相应只读状态。有效且仍获授权的已有答案可以查看，不能据此开放新写入。

超出时间窗口仍允许填写当前访视，沿用现有提醒规则。提交患者表单不会自动完成访视，也不会提前开放下一次访视。

## 5. 数据模型与既有答案迁移

### 5.1 新增实体

| 实体 | 职责与关键约束 |
| --- | --- |
| `PatientLoginIdentity` | 机构、规范化手机号、密码哈希、启用与首次改密状态、密码版本；机构手机号唯一，强制机构 RLS。 |
| `PatientAccess` | 身份与患者档案的明确绑定；患者档案唯一绑定，机构复合外键禁止跨机构关联。 |
| `PatientFormEntry` | 固定患者表单绑定、随机令牌及摘要、启用状态、创建／停用工作人员与时间；每个绑定最多一条有效入口。 |
| `PatientSession` | 会话凭据摘要、机构、患者身份、密码版本、到期／撤销状态及上下文令牌；不保存明文会话凭据。 |
| `PatientSubmissionReceipt` | 患者身份、幂等键、请求摘要和结果答案 ID；身份与键唯一，同键不同内容拒绝。 |
| `PatientActivity` | 患者登录、改密、草稿和提交等操作的主体、目标、时间及必要元数据；追加写入，不记录密码、会话或入口令牌。 |

新业务表均带机构、UUID、必要修订号及创建／更新时间，使用真实 PostgreSQL、FORCE RLS、受限运行账号和机构复合外键。患者身份与临床关联表不授予控制面直接读写权限。

### 5.2 `Answer` 与来源

继续使用“访视＋表单绑定”唯一的 `Answer`，患者和工作人员不能各自生成一份平行答案。

- 当前录入主体支持工作人员账号或患者登录身份，二者恰好有一个；原 `recorded_by` 工作人员外键改为可空，并增加患者主体外键。
- `is_proxy` 表示患者表单是否由工作人员正式代录提交。医生表单始终为 false；患者自填提交为 false；患者表单工作人员代录提交为 true。替换当前“所有患者表单都必须为代录”的数据库约束。
- 正式提交时保存原始提交主体、提交来源和提交时间；这些信息不能被后续修订覆盖。草稿中由谁最终提交，以该次提交的真实主体确定来源。
- 保留当前答案、状态、修订号及更新时间；医生修订只改变当前答案和最近修改主体，不改原始提交主体、来源或时间。

后台列表同时展示填写对象、提交来源、原始提交人、提交时间、最近修改人及更新时间；导出使用相同语义，不能继续将所有患者表单标为“代录”，也不能因工作人员外键为空而报错。

### 5.3 `AnswerRevision` 与历史

每次医生修订保存修改前后完整答案、原修订号、原录入主体、实际修订工作人员、原因及时间。原录入主体支持患者或工作人员，修订主体仍只允许获授权工作人员。

历史记录不可更新或删除，保留现有不可变触发器并扩展约束。前端以该答案固定表单版本的题目名称及选项文案展示前后差异，可展开完整快照。

增量迁移保留现有患者、工作人员、答案、修订及审计 ID。旧患者答案均迁移为工作人员代录；已有正式提交的原始提交主体按最早修订快照中的录入主体还原，无历史时取当前录入主体；旧修订的修改后内容按下一次修订的修改前快照还原，最后一次取当前答案。迁移期间由迁移账号受控补全历史元数据后恢复不可变保护。

已有患者不按联系方式自动开通账号或合并；通过后台明确补开通。迁移不重置工作人员密码，不删除数据卷，不清空业务库。

## 6. 写入规则、修订范围与并发

### 6.1 患者保存和提交

每次写入在同一事务内重新检查入口有效性、机构、患者账号与绑定、研究、正式入组状态、当前访视、填写对象和原发布版本。患者只能写 `respondent=patient`，不能访问医生表单。

草稿沿用已填写值的类型／范围校验；正式提交要求所有可见必填题完成。前后端复用同一表单协议，后端不信任前端的隐藏字段处理或完成标记。

所有保存带 `expected_revision`，冲突返回 409，前端保留本地输入并提示重新加载／核对，不静默覆盖。工作人员与患者同时编辑同一草稿也遵守修订号检查；患者提交后双方只能通过工作人员修订入口改动。

正式提交要求幂等键。重复同键同内容返回已有提交结果，即使首次成功后访视完成或研究暂停，仍可在有效身份、当前授权及有效入口范围内返回既有回执；不能再次写答案。同键不同内容或用于不同任务返回 409。入口撤销、账号失效或授权取消后，不通过幂等回执继续泄露答案。

患者提交与医生保存／修订、访视完成、停止随访、入口撤销和表单暂停使用一致的行锁顺序与重新鉴权。先获得写入许可的事务完成后，后续状态操作生效；状态操作已生效时，等待中的旧写入重新检查并拒绝。实施计划须复用现有研究／患者／入组／访视／表单锁顺序，明确加入入口和患者会话的锁位置。

### 6.2 医生修订

机构管理员或同时满足患者负责关系与研究成员资格的医生可以修订已提交答案，原因去除空白后必填且沿用现有长度限制。

| 答案与业务状态 | 获授权工作人员可否修订 |
| --- | --- |
| 患者表单；研究进行中；当前未完成访视 | 可以。 |
| 患者表单；研究进行中；访视已完成，包括受试者全部访视已完成 | 可以，不重开访视、不改变入组或当前访视状态。 |
| 患者表单；研究进行中；尚未开放的未来访视 | 不可以；正常流程下也不应存在已提交答案。 |
| 医生表单 | 保持原规则：仅当前未完成访视可以修订。 |
| 草稿 | 使用草稿保存接口，不能伪装为正式修订。 |
| 已停止随访、研究暂停／结束、表单暂停或相关对象已删除 | 不可以。 |

保存修订时在同一事务中校验答案修订号、创建不可变历史、更新当前答案及工作人员审计。任一步失败全部回滚。患者本人没有修订权限；不会因为后台增加完成后修订能力而允许患者修改已提交答案。

## 7. 权限、数据库与认证边界

### 7.1 患者请求路径

`/api/patient/` 在中间件中进入独立患者路径，不能借用现有 `workspace_transaction` 或把患者构造成工作人员 `Actor`。后台默认 `ActorPermission` 不接受患者身份；患者接口只接受患者会话。登录前接口不要求患者会话，但登录和所有有副作用请求仍执行 CSRF 校验。

通过限定的入口摘要／会话摘要解析数据库函数取得机构 ID，然后在 `tenant_transaction` 内读取与验证患者数据。解析函数只返回认证所需的机构及记录 ID，不返回患者姓名、手机号、密码哈希、研究内容或答案。

函数固定 `search_path`、撤销 PUBLIC 执行权限，只授权必要运行角色。新入口与会话表为迁移所有者增加仅按当前解析摘要匹配的 RLS 元数据策略，函数仅能匹配调用方提交的高熵摘要，不给任何运行连接增加 BYPASSRLS、超级用户或临床表全局读取权限。

患者身份、绑定、入组、访视及答案的机构必须一致。所有患者读取和写入还必须执行“当前登录身份 → 明确患者绑定 → 本研究入组 → 本入口绑定”的对象级校验；机构 RLS 不能替代患者之间的隔离。

### 7.2 前端及跨标签页

患者页面使用独立的认证状态、请求代次和查询缓存；不读取后台活动机构令牌，不触发后台退出或机构切换事件。后台认证 Provider 只挂载后台页面。

患者业务请求携带发起时的患者会话上下文令牌。重新登录、改密轮换或退出时取消旧请求并清理患者缓存；同源其他患者标签页重新校验状态。服务端对旧令牌返回 409；前端丢弃迟到响应，不能依赖广播到达才保证隔离。正在提交的旧会话写入与会话轮换／撤销之间使用事务屏障，轮换完成后旧写入不能再获准。

患者 API 和页面返回 `Cache-Control: no-store`；浏览器不在 localStorage 保存密码、会话或未提交答案，避免共用设备遗留临床内容。页面刷新可以从服务器已保存草稿继续填写，未保存内容离开页面时提示确认。

## 8. API 与前端体验

### 8.1 后台 API 职责

- 患者账号开通：接收获授权患者、规范化登录手机号及患者修订号，原子建立／复用账号并绑定；返回绑定状态，不返回密码哈希。
- 患者入口候选：按当前表单列出本人可管理的研究、访视、发布版本和入口状态。
- 入口管理：按绑定查询／创建当前入口，停用和重新生成带修订号；所有入口变更记录工作人员审计。
- 既有访视答案、研究答案、答案详情、修订历史和导出：扩展来源信息及可修订状态，权限保持一致。

### 8.2 患者 API 职责

| 接口 | 职责 |
| --- | --- |
| `GET /api/patient/csrf/` | 取得 CSRF 令牌，不读取临床数据。 |
| `POST /api/patient/entry/resolve/` | 校验共用入口并建立认证路由所需上下文；不返回临床信息。 |
| `POST /api/patient/auth/login/` | 入口令牌、手机号和密码；设置患者 Cookie，返回下一步状态和会话上下文令牌。 |
| `GET /api/patient/auth/me/` | 返回最少患者认证状态及首次改密标记。 |
| `POST /api/patient/auth/change-password/` | 原密码及新密码；更新凭据与会话。 |
| `POST /api/patient/auth/logout/` | 撤销当前患者会话并清理 Cookie。 |
| `POST /api/patient/tasks/resolve/` | 已认证且完成首次改密后，按入口令牌返回本人患者候选、任务状态和必要展示信息。 |
| `GET /api/patient/entries/<token>/patients/<patient_id>/` | 返回获授权任务、固定版本定义和现有答案；不能返回其他表单或临床档案内容。 |
| `POST /api/patient/entries/<token>/patients/<patient_id>/answers/` | 草稿或正式提交；服务端确定访视与绑定，拒绝越权及多余字段。 |

错误沿用统一结构：400 为字段校验，401 为凭据／患者会话失效，403 为必须先改密或身份禁止，404 为入口／任务不可用，409 为修订号、幂等键、业务状态或患者会话上下文冲突。

### 8.3 页面

患者入口依次展示登录、首次改密、必要时选择患者、表单填写与提交成功。登录后保留原扫码目标，不能因改密跳到后台首页。顶部展示研究、访视、表单及当前患者，提供退出；不提供后台菜单或机构切换器。

表单复用 `DynamicForm` 和 `FieldControl`。手机宽度从 320 像素起使用单列、完整宽度输入和可换行选项；电脑采用最大宽度约 960 像素的居中内容区。提交和草稿按钮在手机上易于触达，键盘打开时不遮挡输入；长标题、多选项、日期和滑条不得造成页面横向溢出。

提交前显示确认动作，处理中禁止重复点击；成功后显示明确的已提交状态与提交时间。网络失败保留当前输入和原幂等键，可重试；409 显示冲突原因及重新加载入口，不伪装提交成功。

后台答案页以服务端的 `can_revise` 及不可修订原因控制操作，不能继续只使用访视 `writable` 判断。已完成访视中的患者答案可修订时展示“修订答案”，保留只读的访视进度信息。修订历史展示题目级前后差异及完整快照。

## 9. 迁移、交付与验收

使用增量迁移新增患者模块、凭据表和关联表，调整答案主体与历史约束；保留现有不可变历史保护、机构外键、研究状态和工作人员认证。已发布表单不变更，不为旧患者自动创建 `888888` 账号。

更新 README 的患者端说明、初始密码与改密要求、共享号码明确绑定规则、二维码访问地址和本机演示限制。二维码使用当前可访问站点的源地址；手机访问本机开发环境时需要同一网络可达地址或已有部署域名，不能将 `127.0.0.1` 链接当作手机验收成功。

验收覆盖：

1. 新患者同步开通、已有患者补开通、同机构手机号复用、家庭多患者选择、并发开通及配额失败回滚。
2. 初始 `888888` 登录后所有临床接口被服务端阻止，改密后回到原目标；普通改密校验有效，已修改密码不被重复开通或二维码生成覆盖。
3. 同一号码同时作为工作人员与患者，患者登录／改密／退出不影响后台；不同机构患者账号及两类会话相互隔离。
4. 从表单处选择研究和访视生成链接／二维码、重复展示同一链接、下载二维码、停用和重新生成；旧入口立即失效。
5. 多名患者扫描同一码，各自只见本人任务；直接改患者 ID、访视、绑定、表单版本或调用医生接口均无法越权。
6. 移动端和电脑真实浏览器完成登录、改密、草稿恢复、题型校验、正式提交及成功页；320 像素页面无横向溢出。实际手机扫码作为单独设备验收，不能用浏览器移动视口替代。
7. 前后端条件显示和跳题一致，后端拒绝隐藏字段篡改；患者不能填写医生表单或未来访视，超窗当前访视仍可填写。
8. 同键重试只有一份答案；成功后访视完成／研究暂停的授权重试仍返回既有结果；同键改内容拒绝；撤销入口后不能通过回执读取答案。
9. 患者与工作人员同时编辑、提交与访视完成／停止／暂停／入口撤销／会话轮换竞态，使用真实 PostgreSQL 验证锁与状态重新检查。
10. 后台及时看到患者提交，来源和原始提交人准确；代录草稿由患者提交及患者草稿由工作人员代录提交都按最终提交主体记录。
11. 研究进行中可修订已完成访视的患者答案，包括全部访视已完成的受试者；必填原因、前后快照、原始提交主体、提交时间和访视进度均正确。医生表单、停止随访、暂停及结束状态保持规定的锁定范围。
12. 多次修订和并发修订不丢历史，历史 SQL 更新／删除被拒绝；旧答案／旧历史迁移后来源与操作者可追溯，当前答案及 Excel 导出可用。
13. 保留已有工作人员手机号登录、多机构切换、研究入组、代录、访视完成和导出回归；检查迁移一致性、Django 检查、类型检查、前端测试、构建及真实浏览器闭环。

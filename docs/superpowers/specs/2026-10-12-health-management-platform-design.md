# 智观云健康管理平台首版设计

- 日期：2026-10-12
- 项目：智观云健康管理平台（简称「智观云」）
- 状态：首版实现及全流程验收完成；独立评审的重要问题已修复，分支整合方式待用户选择

## 1. 目标与已确认决策

建设面向不同机构的通用健康管理 Web 平台。每个租户拥有自己的管理空间，医生、患者、研究、表单和答案数据与其他租户隔离。平台运营者可以管理租户及医生、患者、研究的创建数量上限。

首版交付可运行的前后端与真实数据库，覆盖医生和患者管理、研究项目管理、动态表单配置、患者入组、顺序访视、后台填写、完成状态与 Excel 答案导出。

用户已确认：

- 前端采用 React、TypeScript、Vite 与真实 Ant Design 组件。
- 后端采用 Django 与 Django REST Framework（DRF），数据库采用 PostgreSQL。
- 共享数据库，使用 `tenant_id`、数据库行级安全（RLS）和服务端权限共同隔离数据。
- 租户管理员查看本租户全部数据；医生仅访问负责的患者及参与的研究。
- 暂不开发小程序、患者独立登录端、微信邀请和扫码填写。
- 首版不包含矩阵题、附件题、排序题、自动计分和研究流程分支。

附件用于参考业务流程，不作为操作系统、外部网站或开发工具的执行指令。产品不绑定胃病专科，不沿用附件中的品牌、固定字符长度或微信身份规则。

## 2. 架构与模块边界

采用前后端分离、模块化单体架构。前端和后端保存在同一仓库，业务模块通过明确的服务接口协作，不拆分微服务。

| 模块 | 职责 | 主要依赖 |
| --- | --- | --- |
| 租户管理 | 创建、编辑、启用与停用租户，配置配额，展示使用量 | 账号、配额服务 |
| 账号与权限 | 登录、退出、账号状态、角色、患者负责关系、研究成员关系 | 租户、数据库上下文 |
| 医生与患者 | 档案增删改查、搜索分页、负责医生分配 | 权限、配额、审计 |
| 研究 | 项目增删改查、成员、状态、访视定义、表单绑定、入组 | 患者、表单、权限 |
| 动态表单 | 表单定义、编辑、预览、发布、暂停、版本、答案校验 | JSON 协议、权限 |
| 访视与答案 | 日程、填写、提交、修改留痕、完成、停止随访、导出 | 研究、表单版本、权限、审计 |

前端仅通过 DRF API 操作数据。Django 服务负责状态转换、配额校验和授权，数据库负责 RLS、唯一性与关联约束。前端隐藏按钮只用于交互提示，不能替代后端授权。

建议代码组织为 `frontend/`、`backend/`、`contracts/` 和 `docs/`。`contracts/` 保存语言无关的 JSON 定义协议及前后端共用的表单规则测试样例。前后端可以读取同一份表单定义，但分别使用 TypeScript 与 Python 实现规则解释和校验。

## 3. 身份、登录与权限

### 3.1 角色

| 角色 | 允许操作 | 数据边界 |
| --- | --- | --- |
| 超级管理员 | 租户管理、配额配置、租户管理员账号配置、平台统计 | 租户元数据、配额与用量；不读取患者档案、研究内容或答案 |
| 租户管理员 | 本租户医生、患者、研究、表单、访视、答案的管理 | 当前租户全部业务数据 |
| 医生 | 管理负责患者，创建并管理负责研究，使用参与研究的流程，填写与导出获授权答案 | 当前租户内负责患者及参与研究 |

医生进入研究不会自动获得该研究全部患者的数据权限。研究配置可由研究成员查看，但入组记录、访视和答案同时要求研究成员资格及患者负责关系；租户管理员可访问本租户全部记录。

研究负责人是研究中的负责医生，不新增独立平台角色。负责人可以配置该研究和成员；普通成员不能修改流程。医生可创建表单并编辑自己创建的表单；租户内已发布的表单模板可以供医生查阅和引用，模板读取权限不包含答案读取权限。

医生创建患者时自动成为负责医生。租户管理员可以分配多个负责医生并调整负责关系。医生不能通过修改请求中的医生 ID，为自己获取未授权患者。

### 3.2 登录与会话

平台登录与租户登录区分入口。租户登录使用租户标识、用户名和密码，用户名在租户内唯一。同一用户名可以存在于不同租户，账号和权限独立。患者档案不创建登录账号。

首版采用 Django 服务端会话、HttpOnly Cookie 与 CSRF 校验。登录接口也必须检查 CSRF，不能只依赖已认证请求上的会话认证检查。部署时前端和 API 使用同一站点，开发时由 Vite 转发 API 请求。密码使用 Django 密码哈希机制保存。

业务请求从服务端会话解析身份和租户，并检查账号及租户是否仍启用。不能通过 URL、请求体或自定义请求头切换已登录租户。退出登录、停用账号、删除医生和停用租户后，后续业务请求失效。

登录前仅允许按明确租户标识解析必要元数据并校验该租户凭据，不开放匿名租户列表或业务查询。创建租户同时建立初始租户管理员，首次登录需要修改初始密码。

## 4. 多租户数据库隔离

医生档案、患者、负责关系、研究、研究成员、入组、访视定义、表单及版本、表单绑定、答案和租户审计记录均包含非空 `tenant_id`。租户账号也按所属租户隔离；平台账号、租户元数据、配额及服务端会话属于控制面，不能借此获得业务数据访问权。

隔离要求：

1. 业务表启用 `ENABLE ROW LEVEL SECURITY` 与 `FORCE ROW LEVEL SECURITY`，读策略和写策略均检查事务中的当前租户。未设置租户上下文时拒绝业务读写。
2. 应用运行账号不使用数据库超级用户、表所有者或 `BYPASSRLS` 权限。数据库迁移账号与运行账号分开。
3. 在显式数据库事务内，通过事务级 `set_config(..., true)` 设置服务端确认的租户上下文。提交或回滚后上下文失效，连接复用不能继承上一请求的租户。
4. Django 的事务边界覆盖账号解析后的业务查询与写入；涉及租户账号认证查询时，先设置相应登录上下文再查询凭据。不能仅依赖 `ATOMIC_REQUESTS` 来覆盖中间件中的查询。
5. 关联约束同时验证 `tenant_id` 和关联对象 ID，阻止跨租户父子关系。必要时使用迁移中的复合外键；序列化器也校验所属租户。
6. 编号、用户名等业务唯一性在租户或研究范围内定义，避免其他租户的同名数据影响创建结果。
7. 列表、详情、搜索、统计、批量操作与导出使用相同的授权数据范围。引用其他租户对象统一表现为对象不可用，不返回对方名称等内容。

RLS负责租户边界，Django 的查询过滤和对象权限负责租户内部医生的数据范围。DRF 的列表查询必须主动过滤，不能仅依赖对象权限检查。

首版 Excel 文件在授权事务内完成数据查询与内容生成，再返回下载。不能在事务结束后的流式响应中执行延迟数据库查询。审计记录也纳入租户边界；平台只记录控制面操作。

## 5. 核心数据关系

| 实体 | 含义与关键约束 |
| --- | --- |
| Tenant / TenantQuota | 租户、状态、三个数量上限及当前用量 |
| Account / Doctor | 登录账号与医生档案；医生档案归属一个租户 |
| Patient / PatientDoctor | 租户内患者档案及一个或多个负责医生 |
| Study / StudyMember | 研究项目、负责医生、参与医生、状态 |
| Enrollment | 患者参加某个研究；观察编号及入组编号在研究内唯一 |
| VisitDefinition | 研究中的阶段类型、顺序、时间间隔和允许偏差 |
| Form / FormVersion | 表单目录与不可变的已发布定义版本 |
| VisitFormBinding | 某访视使用的明确表单版本、填写对象和是否必须完成 |
| VisitInstance | 某受试者的一次访视，含计划日期、时间窗口和完成状态 |
| Answer / AnswerRevision | 一次表单填写及提交后修订记录，绑定具体表单版本 |
| AuditEvent | 有权限的操作者、操作对象、时间及必要变更记录 |

患者与研究是多对多关系，通过入组记录关联。首版同一患者在同一研究只能存在一条未删除的入组记录，不支持重复入组。观察编号和入组编号保存为字符串，不固定为附件示例中的六位数字。

表单定义和答案内容保存为 JSON，身份、关联、状态、编号、日期等可检索字段使用关系型列。所有租户业务关联均具备数据库层面的同租户约束。

## 6. 配额、删除与恢复

### 6.1 计数规则

- 医生配额统计未删除的医生档案，租户管理员不计入医生数量。
- 患者配额统计未删除的患者档案，多次参加不同研究不重复计数。
- 研究配额统计未删除的研究项目，草稿、暂停和已结束研究均计数。
- 停用账号或结束研究不释放额度；软删除释放额度，恢复操作重新检查额度。
- 上限为非负整数，零表示禁止创建该类对象。下调上限不能低于当前使用量。

### 6.2 并发与事务

创建、恢复、删除和配额调整统一经过服务接口。创建和恢复时，在事务中锁定当前租户的配额记录，读取实际使用量，校验上限并完成写入。失败时整体回滚。批量操作也遵循同一计数口径，不能先显示成功再由前端纠正。

用量统计是控制面所需的数量信息，超级管理员可以查看；统计接口不返回医生专业档案、患者身份、研究内容或答案。平台数据库连接只拥有控制面权限，不拥有业务表读取权限。跨租户用量聚合由固定查询的数据库函数提供，仅返回租户与三个计数；函数限定执行角色和固定搜索路径，不接受任意 SQL，普通租户运行角色不能调用。平台统计不使用应用运行角色绕过业务表 RLS。

### 6.3 关联数据保护

删除采用软删除，保留历史关联和答案。普通列表默认排除删除记录，租户管理员可以查看回收记录并恢复。

医生尚有负责患者或进行中、暂停的负责研究时，删除前需要转交这些负责关系；也可以选择停用账号。患者尚有进行中的随访时，先停止随访再删除。研究有未结束受试者时，先完成或停止随访，再结束和删除研究。删除患者或研究后，其相关记录不出现在正常业务入口，但保留供本租户管理员审计和恢复。软删除和恢复不会自动改变随访状态，也不会恢复已结束研究或已停止随访。

正在被进行中或暂停研究使用的表单不能删除，避免已经生成的填写任务失去定义。历史版本和答案不因目录中的删除操作物理移除。

## 7. 医生与患者管理

医生列表支持按姓名、账号、状态搜索和分页；档案包含姓名、联系方式、所属单位、科室、职称及状态。租户管理员可以创建、编辑、停用、删除和恢复医生，医生可查看和修改自己的基础资料，但不能自行变更角色或所属租户。

患者列表支持按姓名、档案编号、负责医生和状态搜索；档案包含编号、姓名、性别、出生日期、联系方式、备注及负责医生。年龄从出生日期计算。手机号不作为患者身份的唯一依据，避免家庭共用号码阻止建档。

详情页面展示基本资料、负责医生和获授权的研究参与记录。医生只能编辑负责的患者，不能修改负责关系或跨租户字段。所有新增、修改、删除、恢复和负责关系调整记录操作者与时间。

## 8. 研究与访视规则

### 8.1 研究状态

研究字段包括名称、编号、研究单位、负责医生、说明、计划开始与结束日期。成员和负责医生只能选择本租户未删除医生；负责医生自动属于研究成员。

| 状态 | 允许操作 |
| --- | --- |
| 草稿 | 编辑信息、成员、访视与表单绑定；不允许确认入组 |
| 进行中 | 加入受试者、确认入组、填写、完成访视、停止随访 |
| 暂停 | 保留查看和导出；停止新增入组、填写和访视完成；允许恢复或停止随访 |
| 已结束 | 查看、导出和审计；不新增入组，不修改答案或恢复为进行中 |

发布为进行中前校验访视定义和表单绑定，至少有一个阶段绑定必需表单。研究结束前，所有未结束受试者必须先完成随访或记录停止原因。

### 8.2 访视定义与冻结

阶段类型支持筛选期、基线期、其他访视和结束期。筛选期可选、至多一次且排在最前；基线期有且仅有一次；其他访视可有多个；结束期可选、至多一次且排在最后。首版不配置分支，按照阶段顺序推进。

每个阶段可以绑定多个已发布表单，明确填写对象是医生或患者，以及是否必须完成。基线期时间偏移为零，后续阶段使用相对入组日期的天数及前后允许偏差；后续偏移按流程顺序不递减。

研究生成首条受试者记录后，访视结构、日期偏移与所用表单版本固定。未结束研究可以修改描述和成员，但不能直接改变已有研究的流程。移除成员或调整患者负责关系前，必须先转交该医生尚未结束的随访职责。后续发布的表单版本不会自动替换该研究已经绑定的版本。

### 8.3 入组与推进

加入研究时必须选择已有患者，且负责随访的医生同时属于该患者负责医生和研究成员。租户管理员可以完成该分配。

有筛选期时，受试者先进入筛选中，筛选访视以加入研究日期为时间起点。完成筛选期的必需表单后才能确认入组。没有筛选期时，受试者进入待入组，医生可以直接确认。

确认入组需要填写研究内唯一的入组编号和入组日期，默认日期为当天。系统在同一事务内生成基线及后续访视实例，绑定研究确定的表单版本，重复请求不能重复生成。

当前访视的必需表单全部提交后，医生手动确认完成，下一阶段才可填写。最后阶段完成后，受试者状态变为已完成。时间窗口用于提醒和逾期标记，超出窗口仍允许有权限的医生记录数据，并显示超期情况，不自动跳过或结束访视。

停止随访需要停止类型和原因，未完成访视转为停止，历史答案保留只读。首版不恢复已停止的随访，也不重复入组。

### 8.4 日历

提供按研究、负责医生和日期查看的随访日历与计划列表。展示计划日期、患者、阶段和完成状态；已完成显示蓝色，超过窗口结束日期仍未完成显示红色，未逾期且未完成显示黄色。今天的待办在列表中直接标识。显示的数据范围与列表和答案权限一致。

## 9. 动态表单协议与设计器

### 9.1 首版题型

| 题型 | 主要配置 |
| --- | --- |
| 单行文本、长文本 | 标题、说明、必填、长度限制 |
| 数字 | 标题、必填、最小值、最大值、小数位数 |
| 日期 | 标题、必填，答案使用日期字符串 |
| 单选、多选、下拉 | 稳定选项 ID、选项文案、必填；多选数量限制 |
| 滑动条 | 最小值、最大值、步长、必填 |

题目与选项使用稳定 ID，显示顺序和文案不作为答案存储键。设计器支持添加、删除、复制和移动题目，批量输入选项，以及必填、条件与跳题配置。题目复制生成新 ID，不复制指向原题的无效关系。

界面左侧选择题型，中间编辑和排序题目，右侧设置当前题目的属性。预览使用与实际填写相同的渲染和规则解释逻辑，但不会创建患者答案。

### 9.2 条件与跳题

显示条件只引用排在当前题目前的题目，支持相等、不相等、多选包含、数字比较和已填写判定。多个条件可以选择全部满足或任一满足，不支持嵌套条件组或执行任意脚本。

单选与下拉可以按选项跳到后续题目。跳题目标必须存在且排在当前题目之后，拒绝回跳、循环和无效引用。目标题被显示条件隐藏时，继续到其后第一道可显示题。

条件隐藏或跳过的题目不参与必填校验，变化后不保留其当前答案。服务器重新计算可填写题目并移除隐藏或跳过的值，拒绝未知题目 ID、非法选项 ID、错误类型或越界值。

JSON Schema 用于定义配置结构及通用数据约束；显示与跳题语义由明确的规则协议定义。前后端分别实现解释器，使用 `contracts/` 中同一批样例验证题目可见性、顺序及答案校验结果一致。

### 9.3 发布与版本

未发布定义为可编辑草稿。发布前验证题目、选项、条件引用和跳题目标，生成不可变的发布版本。修改已发布表单需要创建新草稿，再发布新版本。既有研究和答案保持原版本。

暂停表单后，所有版本的草稿保存、正式提交和答案修订均暂停，历史答案仍可查看；恢复后继续使用对应的原绑定版本。设计器展示哪些研究引用该表单，暂停时明确提示对待填任务的影响。

删除未被进行中或暂停研究使用的目录记录采用软删除，已发布版本及其历史引用保留。一个访视中的一次表单绑定只允许一份当前答案；同一表单在不同访视中分别生成答案，首版不支持同一绑定无限多次填写。

## 10. 答案、修改与导出

医生表单由获授权的医生或租户管理员填写。患者表单由相同范围的工作人员代录，保存患者这一填写对象、实际录入账号和代录标识，不假装患者自行登录提交。

填写可以保存草稿或正式提交。草稿校验已填写值的类型和范围，正式提交还要求所有可见必填题完成。同一次正式提交请求重复发送时返回既有提交结果，不增加重复答案，也不静默覆盖已提交内容；修改已提交内容必须进入答案修订流程。

已经提交但访视尚未完成的答案可以修正，必须填写原因。每次修正保留原提交或上次修订内容、操作者、时间和原因。完成访视、停止随访或结束研究后答案只读；首版不提供解锁完成访视的入口。

导出范围包括单份答案和研究内获授权答案。研究导出按表单版本分别生成工作表，列包含患者档案编号、研究入组编号、访视、填写对象、录入人、提交时间及题目答案。导出当前答案，修订历史在后台单独查看。

导出前检查与页面相同的数据权限，记录导出人、时间、范围和数量。文件名和临时存储键不含患者姓名；字符串按文本写入，防止用户填写值被 Excel 解释成公式。首版不公开持久下载链接，也不导出其他租户或其他医生负责患者的数据。

## 11. 管理界面与组件

采用 Ant Design 标准后台布局和默认交互习惯。使用中文界面、左侧导航、顶部租户及账号信息、面包屑和内容区域，蓝色为主要操作色。

| 页面 | 内容与组件 |

## 12. API、错误与一致性

API分为平台控制面、租户认证及租户业务路由。平台和租户分别校验角色，不能通过平台角色直接调用患者业务接口。

列表使用统一分页结果，筛选参数由后端校验。创建时的 `tenant_id`、录入人和创建人由后端设置；客户端不能覆盖这些字段。更新不能修改租户或表单版本归属。

错误采用稳定错误代码、中文说明和字段错误信息：

- 凭据无效、会话失效、账号或租户停用。
- 对象不可用、无操作权限。
- 配额不足、恢复超额、下调额度低于使用量。
- 编号冲突、重复入组、跨租户关联非法。
- 表单定义错误、必填未完成、答案值无效、表单已暂停。
- 研究流程已固定、研究或访视状态不允许当前操作。
- 编辑版本冲突，要求刷新后重新修改。

入组、生成访视、提交答案、访视完成、停止随访、删除恢复和配额调整使用事务。可重复调用的动作提供幂等结果，状态转换锁定目标记录；错误不能留下半完成数据。可编辑的档案、研究信息和草稿使用修订号避免覆盖他人刚保存的修改。

## 13. 验证与验收

数据库相关验证必须运行在真实 PostgreSQL 上，不能用 SQLite 代替 RLS 验证。用与生产权限一致的应用数据库角色执行隔离测试，同时覆盖直接 SQL 与 API。

| 验证范围 | 必须通过的场景 |
| --- | --- |
| 租户隔离 | 两租户同名数据互不影响；跨租户列表、ID 查询、修改、关联、统计和导出均无法越界 |
| 上下文 | 缺少租户拒绝业务数据；连接先处理甲租户再处理乙租户不会继承甲的上下文；异常回滚后也不泄漏 |
| 医生权限 | 同租户两医生不同负责患者互不可见；仅成为研究成员不能读取其他医生患者的答案；权限变更及时生效 |
| 平台权限 | 超级管理员可配置租户与配额，但不能查看患者、研究内容或答案 |
| 配额 | 创建、停用、结束、删除、恢复口径一致；最后一个名额的并发请求至多一个成功；事务失败不消耗额度 |
| 表单规则 | 前后端样例结果一致；隐藏或跳过的必填题不阻塞；禁止循环和无效引用；篡改提交由后端拒绝 |
| 版本 | 新发布版本不改变既有研究、旧答案展示或按版本导出 |
| 研究闭环 | 建档、创建研究、发布表单、配置访视、筛选、确认入组、代录、提交、完成、日历和 Excel 导出连贯可用 |
| 边界状态 | 暂停、停用、停止随访、已完成和软删除后符合读写规则；重复请求不生成重复数据 |
| UI | 超级管理员、租户管理员、医生的菜单和操作一致；动态表单设计、预览及实际填写可在浏览器完成 |

首版提供明确的本地启动说明、环境变量示例、数据库迁移和仅含虚构数据的演示初始化。演示至少包含两个租户、各角色账号和两名不同负责范围的医生，用于实际演示隔离和完整研究流程。

部署材料包括前端构建、Django 服务与 PostgreSQL 的启动配置。密钥和真实用户数据不写入仓库。上线托管、外部服务接入和小程序开发不属于本次首版交付。
